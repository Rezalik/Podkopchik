# AX6000 Xray FD Exhaustion In An AWG-Only Configuration

Date: 2026-11-05, Europe/Moscow. Only Xiaomi Redmi AX6000 via `ssh openwrt`.
No access to openwrt2, firmware/core/module/package update, VLESS restoration,
role change, network/SSH/Wi-Fi change or UDP/IPv6 policy change.

## Confirmed Incident

The live main Xray PID 304 reached 4095 open descriptors, with soft/hard limits
4095/4096. It repeatedly logged `accept4: too many open files` for the
transparent 12345 and DNS 1053 listeners. Individual AWG HTTPS probes succeeded,
CPU was low and RAM available: a healthy tunnel did not imply that the shared
transparent/DNS process could accept new client sessions.

The active configuration was checked, not inferred from deleted VLESS entries:
three AmneziaWG profiles, no VLESS; Xray TPROXY/DNS/FakeDNS, 81 domain rules,
8 IP rules including reserved routing, and marked/interface-bound AWG freedom
outbounds. It genuinely handles user traffic in this AWG-only configuration.

## Why The Limit Was Reached

At the first socket sample, 3896 UDP and 17 UDP6 socket-table entries dominated
the 4095 FD total. UDP6 entries can be dual-stack sockets and do not establish
that IPv6 interception was enabled. A later sample had one UDP local-port 443
binding and 3940 other-port bindings; 6881 and 51413 were frequently repeated.
Most were not bound to the FakeDNS pool. These are local socket observations,
not proof of a specific client application or provider-visible session count.

Generic UDP interception is enabled. Even unmatched traffic that eventually
goes direct enters the same Xray process. Aggregate conntrack showed a large
UDP source at LAN 192.168.1.144, DHCP hostname `mediaserver`. P2P-like port use is
an investigative lead, not proof that a torrent client caused the incident.
Video activity may expose an already exhausted shared limit without creating
all the retained sockets itself.

Upstream26.3.27 uses UDP worker connection state and inactivity cleanup, and
dokodemo PacketWriter can retain multiple transparent response sockets until
its writer closes. These mechanisms explain why local FDs need not track the
current WAN-flow count one-to-one; they do not prove an upstream leak on this
router. See [UDP worker](https://github.com/XTLS/Xray-core/blob/v26.3.27/app/proxyman/inbound/worker.go)
and [dokodemo writer](https://github.com/XTLS/Xray-core/blob/v26.3.27/proxy/dokodemo/dokodemo.go).
No timeout, UDP mode or Xray core code was changed.

A post-change IPv4 sample found 305 non-local-address UDP bindings; 192 had no
matching remote endpoint in the current conntrack snapshot. This supports
retained transparent reply-socket state rather than one live WAN connection
per FD. It does not attribute each socket to a LAN application or prove a leak.

One separate IPv4 conntrack sample counted 318 WAN-related TCP and 486 UDP
entries, including 5 outer AWG UDP entries. These are local tuple-based flow
estimates, not the provider's active-session counter or blocking threshold.

## Narrow Mitigation

The shared `xray_instance()` now sets:

```sh
procd_set_param limits nofile="16384 16384"
```

This applies to startup, controlled restart, recovery and failover core starts.
It does not raise health-worker or system-wide limits. procd accepts the
soft/hard pair through its [resource limit handling](https://github.com/openwrt/procd/blob/master/service/instance.c).

16384 is four times the old hard cap and remains below the observed system
file limit 49460, leaving headroom for other services. Available RAM was about
283 MiB before the restart. The ceiling is not a preallocation or a session
generator; it is immediate capacity mitigation, not a demonstrated fix for
unbounded UDP retention. It must be evaluated with post-change measurements.

Fresh current AWG-only canonical snapshot and independent procd recovery were
prepared under root700 directory:

Only the syntax/hash-checked init file was replaced atomically. A dedicated

existing lock/token scheme and a 1200-second independent watchdog.
The worker verified actual process limits and unchanged configuration.

the serialized Podkopchik nft table matched the pre-change copies byte-for-byte.
Network/AWG config checksums and default route also matched.

Fresh DNS mappings and LAN HTTPS checks returned 200 for YouTube and Instagram.
That tests reachability, not logged-in video playback or long-term stability.

## Eight-Minute Observation And Outcome

The fixed main PID remained 24190 for all 17 samples across 486 seconds.

| Measurement | First | Final | Range |
| --- | --- | --- | --- |
| All descriptors | 929 | 1283 | 926-1294 |
| UDP socket descriptors | 237 | 388 | 237-396 |
| Original UDP inodes still open | 237 | 233 | 233-237 |
| New-PID EMFILE messages retained | 0 | 0 | 0 |

Some sockets closed: four of the original UDP inodes disappeared, and later
UDP counts fell from 396 to 388. However, **net UDP and total FD growth continued**
over the window. The higher cap restored capacity; this is not proof that
long-term retention is fixed or that the new ceiling cannot be reached later.
Continuous traffic can keep UDP associations active; a controlled idle/source
comparison or longer bounded observation is still needed to separate legitimate
retention from a leak. No client application was stopped to force that result.

A later final read-only check found 1476 descriptors on the same PID, still
with limits 16384/16384 and zero retained new-PID EMFILE messages. Thus net FD
growth persisted beyond the formal eight-minute window. Do not describe the
hotfix as stopping accumulation; renewed exhaustion under sustained churn
remains a risk requiring separate follow-up work.

The operator reported that video worked during five minutes of checking.
Fresh LAN YouTube and Instagram HTTPS probes both returned 200, with zero new
EMFILE errors during monitoring. Main Xray RSS was 67616 KiB near the end;
MemAvailable was approximately 288-323 MiB across the recorded samples and the
separate final check. The health daemon kept its old limits (1024/4096), the
system file maximum stayed 49460, and no default route or role changed.

The hotfix was committed after the bounded checks. Independent rollback timer
and installer worker were removed; only normal services and owned routing
remain. No reboot, extra Apply or GitHub push. A future Apply/core restart/boot
uses the centralized new main-process limit; actual reboot was not tested.

## Regression Checks And Recovery

Shell syntax checks (58 files), JSON checks (3 files), safe Apply, core-only
restart and startup recovery smokes passed. Tests assert the limit on main
creation/recovery and its absence from health-only startup. LuCI runtime Apply
and i18n coverage smokes, docs links/fences and `git diff --check` passed.
No LuCI source or translation catalog was changed.

Changed implementation files are `root/etc/init.d/podkopchik` and the two
focused startup/restart tests. README, SPEC, ACCEPTANCE, this incident report
and the separate architecture assessment document the scope and limitations.

The private canonical snapshot above captures the current AWG-only roles and
configuration, not historical VLESS. To roll back, prepare a new root700
directory with that snapshot/hash and the saved watchdog/guard-lock helpers,
then use the established independent `arm`/`request` procedure in
[the r7 recovery guide](AWG-STAGE4-R7-LIVE-20261104.md#future-recovery).
Do not reuse the committed directory or unpack a full/private archive over `/`.
Reverting the old limit may reproduce the capacity failure; investigate UDP
retention rather than repeatedly restarting to hide it.
