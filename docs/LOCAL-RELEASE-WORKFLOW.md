# Локальная Разработка И Обновления Native

## Основной Порядок

1. Разрабатываем на Mac в `feature/universal-routing-engine`.
2. Проверяем код, регрессии и затронутые сетевые сценарии в изолированной VM.
3. Собираем полный ARM64-пакет дважды, сравниваем архивы и проверяем SHA256.
4. Публикуем исходники в feature-ветке, а пакет — отдельным GitHub prerelease
   с тегом `native-rc-*`. Не выдаём его за стабильную версию.
5. На роутере устанавливаем обновление через LuCI, затем выполняем обычный
   Native Apply, проверяем сеть и подтверждаем поколение.

На роутере не редактируем исходники, не собираем Go/Node и не обновляем Xray,
ядро OpenWrt или AWG вместе с приложением. Рабочая конфигурация не должна
превращаться в набор разрозненных SSH-патчей.

## Подготовка На Mac

Нужны Git, Node.js для локальных проверок, gettext, tar/gzip и закреплённый
Go 1.26.10. Эти зависимости нужны компьютеру, не роутеру.

```sh
git switch feature/universal-routing-engine
sh tools/check-native-local.sh
(cd native/dns && go test -mod=readonly ./...)
sh tools/build-native-candidate.sh "$PWD/.build/release-a"
sh tools/build-native-candidate.sh "$PWD/.build/release-b"
cmp .build/release-a/*.tar.gz .build/release-b/*.tar.gz
node tools/verify-native-candidate.js .build/release-a/*.tar.gz
```

SKIPPED на Mac не заменяет VM-проверку. Перед выпуском изменений routing/DNS
нужно повторить соответствующие VM-сценарии. GitHub Actions не имеет доступа
к домашнему роутеру и не выполняет физическую приёмку.

Если исходники самого helper в `native/dns` и рецепт компиляции **побайтово не изменились**,
можно переупаковать прежний проверенный helper:

```sh
sh tools/build-native-candidate.sh "$PWD/.build/release-a" \
  --reuse-helper-from "$PWD/.build/native-candidate/podkopchik-native-ax6000-candidate.tar.gz"
```

Сначала проверяется весь прежний архив и совпадение исходников/рецепта.
Каталог `cmd/` с отдельными диагностическими программами не входит в helper;
его изменения не требуют замены неизменившегося DNS-бинарника.
Это не новая компиляция ARM64, а повторное использование неизменного компонента.
При любом изменении DNS-компонента нужна полная сборка с Go.

## Публикация В GitHub

Коммитьте только исходники, тесты, переводы и обезличенную документацию.
Не добавляйте `.router-backups`, `.build`, `tests/.tmp.*`, `.DS_Store`,
UCI-снимки, AWG-ключи, рабочие VLESS URI и пароли. Не используйте force push.

После коммита и проверки состава:

```sh
git push origin feature/universal-routing-engine
git tag native-rc-20261108-1
git push origin native-rc-20261108-1
```

Имя тега каждый раз новое; пример выше не переиспользовать для другой сборки.
Workflow `.github/workflows/native-rc.yml` проверяет принадлежность коммита
feature-ветке, запускает локальные тесты, дважды собирает пакет и публикует
**prerelease**, не stable/latest. Обычный push feature-ветки создаёт только
артефакт, без релиза; push нового тега публикует prerelease. `main` не меняется.
Используется событие push: ручная кнопка workflow_dispatch требует файла в
default-ветке и поэтому здесь не нужна ([события GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).
Разрешение `Contents: write` нужно заданию
публикации, а не исходникам или роутеру; токены не записываются в репозиторий.

Релиз содержит:

- `podkopchik-native-ax6000-candidate.tar.gz`;
- файл `.tar.gz.sha256`;
- внутренние `SHA256SUMS`, `TARGET`, `NATIVE_DNS_SHA256`.

GitHub автоматически задаёт SHA256 asset в API ([документация](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28)). Без этого digest обновлятор
не принимает пакет. Контрольная сумма защищает целостность, но не является
отдельной криптографической подписью автора: доверяем HTTPS и доступу к репозиторию.
Пакет привязан к конкретной плате и проверенному набору OpenWrt 25.12.6 /
mediatek/filogic / ARM64 / ядро 6.12.112. В каталоге есть AX6000 stock и
Flint 2. Сборка для Flint доступна отдельно:

```sh
sh tools/build-native-candidate.sh "$PWD/.build/flint-lab" --target flint2 \
  --reuse-helper-from "$PWD/.build/release-a/podkopchik-native-ax6000-candidate.tar.gz"
node tools/verify-native-candidate.js .build/flint-lab/*.tar.gz
```

Оба архива используют одни и те же общие файлы и ARM64-бинарник. Их
`PLATFORM.json` и имена файлов различаются. Flint публикуется только как
артефакт тестовой сборки, не как доступное обновление. Модель вне каталога
не допускается автоматически. См. [план переносимости](NATIVE-PORTABILITY.md).

## Разовый Переход Со Старого Обновлятора

Уже установленная версия не получает новый механизм одним фактом push.
Не нажимайте старую кнопку обновления из `main` поверх Native.

После согласования обслуживания скачайте релиз на Mac и выполните
`node tools/verify-native-candidate.js ПУТЬ_К_АРХИВУ`. Сверьте SHA256 с GitHub.
Сохраните приватный бэкап на Mac. На роутер переносится только проверенный
пакет в закрытый каталог `/tmp`; повторно проверяется его SHA256. После
распаковки выполните из корня пакета:

```sh
sh install-native-dns.sh --preflight
sh tools/install-native-rc-files.sh "$PWD"
```

Статический установщик проверяет все целевые пути до записи, сохраняет
предыдущие файлы в ограниченном временном каталоге и восстанавливает их при
ошибке записи. Не устанавливает системные пакеты, не меняет UCI и не запускает
службы. После проверки удалите перенесённый архив/распаковку; это не рабочее
DNS-состояние. Для доступа к новым LuCI ACL/переводам может потребоваться
отдельное согласованное обновление rpcd/uhttpd и повторное открытие LuCI.

Это разовое обновление в данной задаче **не выполнялось на Xiaomi**.

## Дальнейшие Обновления Через LuCI

1. Откройте «Podkopchik → Обновления → Проверить».
2. Убедитесь, что источник — `native-rc`, тег — ожидаемый, пакет для вашей платы.
3. Нажмите «Установить обновление» и дождитесь завершения задания.
4. Откройте «Статус», выполните обычный Apply. Проверьте DNS, Direct,
   защищённые сайты и приложения с домашнего устройства.
5. Подтвердите Native Apply до его дедлайна. Без подтверждения действует
   обычный транзакционный откат к предыдущему подтверждённому поколению.

Обновлятор не использует исходный tarball ветки и не откатывается к Legacy,
если Native prerelease отсутствует. Он сохраняет настройки и профили,
историю synthetic-IP и работающее immutable-поколение. До Apply новый код
ещё не обслуживает маршрутизацию. После обновления страниц LuCI обновите вкладку.

Проверяются digest архива, типы/пути/владельцы/размеры tar, внутренний манифест,
целевое устройство и место. Нужно не менее 64 МиБ свободного `/tmp` на старте;
компонент дополнительно требует 48 МиБ свободного `/tmp`, 96 МиБ доступной RAM
и резерв flash 13.5 МиБ плюс новый helper. Фактический архив ограничен 12 МиБ,
распаковка — 24 МиБ. При нехватке места обновление прекращается, пользовательские
файлы не удаляются. Не запускайте параллельные обновления/Apply.

## Отказ И Восстановление

Ошибка скачивания, SHA256, архива или preflight не запускает новый движок.
Ошибка публикации статических файлов возвращает старые файлы; подтверждённый
Routing Core продолжает работать из своей неизменяемой копии. Новый helper
устанавливается по хешу и может остаться неиспользуемым после неудачной попытки;
его нельзя удалять, не проверив ссылки поколений.

После неудачного Apply используйте штатный transactional rollback или
`native-abort` с действующим pending-токеном. Кнопка Legacy rollback **отклонена
для Native**, она не восстанавливает DNS ledger и поколение. Подтверждённые
поколения и историю выдачи synthetic-IP не заменяйте старым tar-бэкапом.
Ремонт после потери питания во время файловой установки требует проверенного
полного пакета и доступа к управлению; статическое обновление не заявляется
единой атомарной заменой всех файлов flash. Автоматический reboot не выполняется.
