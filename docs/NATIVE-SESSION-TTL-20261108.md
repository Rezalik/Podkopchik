# Native: срок DNS и срок установленного соединения

Дата: 8 ноября 2026 года. Статус: **исправление установлено на Xiaomi с отдельного
разрешения пользователя; Native Apply подтверждён, пользователь отметил улучшение,
но сохранились короткие паузы 3-5 секунд**. Пользовательские настройки сохранены.

## Симптом и диагностика

Пользователь сообщил, что после длительного просмотра Instagram видео
перестаёт загружаться примерно на 30-60 секунд. Подключение телефона напрямую
к тому же AWG при этом работает.

На Xiaomi AX6000 проверены действующие Native и три AWG. В снимке до изменений
DNS имел 11 FD и 2 собственных UDP-сокета, доступной RAM было около 316 МиБ,
conntrack занимал 957 из 31232 записей. Xray не работал, все три AWG были UP.
Нового переключения транспорта или смены DNS PID не обнаружено.

В последующем обезличенном снимке рабочего роутера найдено 14 Instagram-соединений,
включая 5 установленных TCP-соединений. У одного установленного соединения
срок DNS-сопоставления уже истёк. Три Instagram-соединения не имели действующей
записи в nft map. Счётчик блокировки синтетического пула увеличивался.
Адреса клиентов, имена просмотренных ресурсов и содержимое трафика не сохранялись.

Это подтверждает наличие дефектного состояния на роутере и согласуется с
симптомом. Точная синхронизация конкретного iPhone и момента каждой паузы ещё
не выполнена; это не доказательство отсутствия других причин торможения.

## Подтверждённый дефект

`native/dns/lease.go` публикует nft map и набор политики со сроком DNS TTL плюс
30 секунд. Ранее `universal_plan.uc` заново требовал действующее сопоставление
для каждого исходящего пакета, включая пакеты уже установленного TCP.
После удаления записи срабатывала блокировка синтетического пула.

На изолированной OpenWrt VM дефект воспроизведён: первое обращение по одному
TCP keepalive-соединению прошло; после истечения nft lease повторное обращение
по тому же соединению завершилось таймаутом. AWG-подобный тестовый транспорт,
маршрут и HTTP-сервер не останавливались. После обновления сопоставления новые
TCP/UDP-запросы снова работали, а Direct оставался доступен.

DNS TTL определяет срок использования DNS-ответа для новых обращений, но не
должен самостоятельно отзывать ранее разрешённое соединение. Ядро сохраняет
DNAT в conntrack для последующих пакетов: см.
[официальное описание stateful NAT](https://wiki.nftables.org/wiki-nftables/index.php/Performing_Network_Address_Translation_%28NAT%29).

## Узкое исправление

Перед обычной классификацией по timed DNS-наборам добавлены правила продолжения
соединения. Одновременно необходимы:

- правильный входной LAN и адрес из текущего synthetic-пула;
- исходное направление, `ct state established` и `ct status dnat`;
- принадлежащий Podkopchik conntrack pin конкретного транспорта;
- доступный транспорт и поддержка семейства адресов;
- TCP/UDP для AWG либо только TCP для текущего VLESS-адаптера.

Сначала применяются действующие правила LAN-клиентов. Затем восстанавливается
только packet mark того же транспорта, без переноса NAT tuple на другой адаптер.
Обычные egress-guards и проверка transport pin остаются на пути пакета.

Это не общий `accept established` и не увеличение DNS TTL. Новое соединение
к просроченному либо неизвестному synthetic-IP по-прежнему блокируется.
Не создаётся Direct-fallback. Retired-пулы проверяются раньше продолжения
соединения. All-down и исчезновение классификатора также блокируют старые tuple.
Уже разрешённый tuple остаётся привязанным к транспорту до закрытия/истечения
conntrack, а не переезжает вслед за изменением DNS-ответа.

## Воспроизведение

`tools/native-session-ttl-vm-test.sh` запускается в подготовленном NIC-free
OpenWrt-стенде с `/mnt/lab/source`, проверенными тестовыми бинарниками,
ip-full, veth и tcpdump. Скрипт проверяет VM-модель до создания namespace,
использует отдельные namespace и очищает их через trap. На роутере его
запускать нельзя.

`tests/native_synthetic_sessions_smoke.sh` выполняет чистую Ucode-проверку
планировщика и явно возвращает SKIP при отсутствии ucode на Mac.
В общем DNS VM-наборе требование «убить установленный TCP после DNS TTL»
заменено проверкой сохранения этого соединения и блокировки нового.

## План установки и отката

### Выполненное внедрение

С отдельного разрешения установлен только `universal_plan.uc`, SHA256:
`5c7f25942c6cfbb26f8b592b9c45dd3cee3ec264ddc4894fa83e222fb5a89c54`.
Выполнен ровно один обычный Native Apply, подтверждённый 8 ноября 2026 года
в 18:21:22 МСК. Новое поколение: `4c0756219c48bfa5a949adf52b46df9d`,
`pending=null`, `repair=false`, выборочная политика прежняя, правила 81/7/0.

Совпали контрольные суммы UCI, AWG-профилей, fw4, default routes и policy rules.
Ifindex всех трёх AWG сохранились. DNS намеренно сменил PID 29012 на 7629;
это не доказательство исправления накопления сокетов. Наблюдатель PID5066,
dnsmasq4767, SSH1608 и uhttpd17498 не менялись, reboot не выполнялся.
Отдельная аварийная служба не восстанавливалась, Xray не запускался.

Проверки после подтверждения: Validate Active PASS, клиентские DNS UDP/TCP,
защищённый и Direct HTTPS PASS, HTTPS через три AWG PASS, Direct UDP-контроли
PASS. Правила продолжения установленных соединений уже пропускают пакеты.
В контрольном снимке: FD11, UDP2, RSS около 13,4 МиБ, CPU системы около 9,8%,
доступная RAM около 322,5 МиБ, conntrack1615/31232. Свободно 40660 КиБ overlay.

Исходное окно наблюдения не продлено и не начато заново: это пятый PID-сегмент
и отдельная версия кода внутри исходной приёмки. Пользователю предложен
просмотр Instagram 10-15 минут без клиентского VPN. В ответ пользователь сообщил
три паузы примерно по 3 секунды и одну примерно на 5 секунд, назвав результат
терпимым. Это качественная пользовательская оценка улучшения относительно
прежних пауз 30-60 секунд, а не инструментальный замер или доказательство
полного устранения проблемы. Фактическая длительность теста отдельно не измерена.
Причина оставшихся коротких пауз не установлена; дополнительных изменений
после этого сообщения не выполнялось. Общая долговременная стабильность
и полное отсутствие видеопауз по-прежнему не подтверждены.

### Проверяемый порядок

1. Получить разрешение на одно краткое окно Native Apply.
2. Сверить board, активную generation и SHA256 установленного/исправленного
   `universal_plan.uc`. Сохранить прежний модуль приватно, не публикуя профили.
3. Проверить синтаксис, генерацию и транзакцию nftables до переключения.
4. Установить только исправленный модуль и выполнить один штатный Native Apply
   с прежними UCI, ролями, профилями, DNS-настройками и выборочной политикой.
   Он кратко перезапускает управляемый Native DNS. AWG, Wi-Fi и default route
   вручную не перенастраиваются. Удалённую аварийную службу не восстанавливать.
5. Проверить DNS, защищённый HTTPS, Direct, собственные правила и интерфейсы;
   подтвердить Apply только при успешных критических проверках. Затем проверить
   длительный Instagram с телефона и повторно измерить ресурсы.
6. При неудаче незавершённого Apply использовать его штатный abort/rollback.
   Вернуть прежний статический модуль для последующих Apply. Не откатывать
   allocator watermark и не удалять журнал synthetic-IP.

ARM64 DNS-бинарник не менялся, пересборка ядра, Xray либо AWG для этой правки
не нужна. До физической приёмки нельзя объявлять Instagram или общую
долговременную стабильность исправленными.
